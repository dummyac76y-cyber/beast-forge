# Beast Forge AI Studio

An **optional, development-time** toolkit for the Beast Forge repository. It
generates and validates game assets, inspects the environment, and runs browser
QA.

> The AI Studio is never a runtime dependency. Delete this whole directory and
> the game still builds, ships and plays — it falls back to procedural vector art
> and synthesised audio. `npm run verify` and the QA suite both assert that.

Governed by the master skill at `.kilo/skills/beast-forge-ai-studio/SKILL.md`.

---

## Quick start

```bash
npm run doctor     # what is actually available in this environment
npm run verify     # asset contract + file integrity + headless battle sim (no browser)
npm run qa         # real-browser QA via Playwright
npm run check      # verify + qa
```

Asset pipeline (two phases — generation never touches the game):

```bash
npm run assets          # render into tools/ai-studio/{art,audio}/outputs/
npm run assets:promote  # copy into web/assets/ and merge assets/manifest.json
```

Promotion **refuses to overwrite** any existing game asset. Pass `--force`
through to `generate-assets.mjs` if you genuinely mean to replace one.

**None of the shipped art or audio was generated by a model.** With no GPU and no
engines installed, `scripts/lib/art.mjs` draws the sprites and `renderCue()`
synthesises the clips procedurally and deterministically. That is a deliberate
substitution, not a claim of AI generation: the alternative would have been
fabricating output and reporting it as model-generated.

To use a real provider later, add it behind the same manifest contract the
renderer already consumes — the game needs no changes.

## What the assets are

Ten sprites and eighteen audio cues, all wired through
`web/assets/manifest.json` (the manifest that shipped with the web port; the
promote step **merges** into it and preserves its `_readme` and font credits).

| Key | File | Notes |
|---|---|---|
| `unit_biped` | `sprites/units/biped_v001.png` | 78×78, bear/werewolf/gorilla/lizard |
| `unit_quadruped` | `sprites/units/quadruped_v001.png` | 102×78, tiger/lion/rhino/hippo |
| `unit_dragon` | `sprites/units/dragon_v001.png` | 126×126 |
| `fort_player` | `sprites/forts/fort_player_v001.png` | 120×275 |
| `fort_enemy` | `sprites/forts/fort_enemy_v001.png` | 120×275 |
| `bg_forest` `bg_volcano` `bg_snow` `bg_citadel` `bg_arena` | `sprites/bg/…` | 1024×576, `cover: true` |
| 18 audio keys | `audio/*.wav` | mono 22.05 kHz, keys match `web/js/audio.js` `CUES` |

### Two design decisions worth knowing

**Unit art is neutral on purpose.** `render.js` keys sprites by *race* only —
`unit_biped` serves fire, ice, earth, wind, lightning and poison beasts alike.
Baking an element colour into the art would be wrong for five of six cases, so
the palette is neutral stone and the renderer draws the element aura on top.

**The WebGL renderer does not read the manifest.** `render3d.js` builds its own
`CanvasTexture` meshes procedurally and never calls `assets.sprite()`. So the
sprites are used on the Canvas 2D path (`?2d`) and the audio is used on both.
QA reports this explicitly rather than letting it look like the art is
everywhere. Feeding the manifest into the 3D renderer is the natural next piece
of work — it is a renderer change, so it is out of scope here.

## Layout

```
tools/ai-studio/
├── README.md
├── scripts/
│   ├── doctor.mjs            # honest environment + provider status
│   ├── verify.mjs            # contract + integrity + headless engine sim
│   ├── generate-assets.mjs   # staged generation, explicit promotion
│   └── lib/
│       ├── spec.mjs          # THE asset contract (keys, sizes, anchors)
│       ├── art.mjs           # sprite + background drawing
│       ├── raster.mjs        # tiny software rasterizer
│       ├── png.mjs           # PNG encoder (zlib only)
│       └── wav.mjs           # WAV encoder
├── qa/
│   ├── serve.mjs             # zero-dep static server for web/
│   ├── run-qa.mjs            # Playwright suite
│   └── shots/                # gitignored screenshots
├── art/outputs/              # gitignored staging area
└── audio/outputs/            # gitignored staging area
```

### Zero runtime dependencies

`png.mjs`, `wav.mjs` and `raster.mjs` are hand-rolled on top of Node's `zlib`.
The host had no image libraries (no Pillow, no npm packages), and pulling in
`sharp`/`canvas` would have meant native builds for a task that only needs
`deflate` and a scanline filler. Playwright is the sole dependency and it is
dev-only, used solely by the QA suite.

### Determinism

There is no `Math.random()` anywhere in the generator — noise comes from an
integer hash. Re-running `npm run assets` produces byte-identical files, so
regenerating art does not create meaningless diffs.

## `verify.mjs` — the contract guard

The interesting part is layer 1. Rather than trusting `spec.mjs` to stay in sync,
`verify.mjs` re-derives the sprite and audio keys **from the game source**:

- unit keys from the race constants in `models.js`
- background keys from the `THEMES` table in `render.js`
- audio keys from the `CUES` table in `audio.js` plus every `play('…')` call site
  and every element/race → cue map in `engine.js` and `ui.js`

If the game starts asking for an asset the manifest does not have, `verify`
fails. This is what stops the manifest from silently rotting.

Layer 3 runs the real `BattleEngine` headlessly through stage 1, stage 6 and an
arena run, playing greedily, and asserts each battle actually resolves.

## QA notes

`run-qa.mjs` drives real Chromium and covers both renderers:

- default — WebGL, forced through SwiftShader so headless Chromium exercises the
  3D path instead of quietly falling back
- `?2d` — Canvas 2D, the path that consumes the manifest sprites
- a degradation pass that aborts every `/assets/**` request and asserts the game
  still boots and plays

Every wait is on a real state condition (HUD clock, fort HP, overlay presence).
There are no blind `sleep` calls except two deliberate 400 ms waits to let mana
regen between deployments.

Two practical gotchas encoded in the suite:

- `#cardbar` is rebuilt every ~120 ms by `ui.js`, so a Playwright `click()` races
  the detach forever. The suite dispatches the click in-page instead.
- Lane hit-testing in `render.js` is `floor((y - 110) / 55)` over a 450-unit-tall
  virtual space, so a click must land at `0.2444 + lane * 0.1222` of canvas
  height to hit lane *n*.

## Known limitations

- No AI generation is wired up yet; all assets are procedural.
- The 3D renderer ignores the manifest (see above).
- QA asserts that a battle reaches *a* terminal state, not that it wins — the
  scripted clicks are not a skilled player.
- Screenshots are gitignored; regenerate with `npm run qa`.
- The Android app still reads from `app/src/main/assets/`. These assets are
  web-only. Porting them means copying the PNG/WAV files across and adding an
  equivalent manifest to the Android asset loader — not done here.
